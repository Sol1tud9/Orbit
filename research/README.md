# Подготовительное исследование

Основная реализация приложения ещё не начата. Исходные материалы организаторов не изменялись.

- `probe.py` — расчёт четырёх полных сценариев неизменённым `geometry.py`, диагностический BFS, независимая проверка минимального числа переходов алгоритмом Флойда — Уоршелла с разрешением транзита только через спутники, метрики, проверки границ отказов и особенностей валидации.
- `findings.json` — результаты эксперимента, интервалы перерывов, сводки состояния каждого отсчёта и SHA-256 исходного модуля и сценариев. Это полученные нами контрольные значения, а не опубликованные организаторами ответы.
- `edge_cases.py` — независимая скалярная геометрия по формулам PDF; 60 состояний с seed=2026, перестановка и переименование объектов, малый сценарий с двумя шлюзами, отключения шлюзов, совпадающие спутники, пересечение отказов, события между отсчётами, строгий порог ISL и включающий порог возвышения; дополнительный расчёт второй очереди.
- `edge-findings.json` — результаты дополнительных экспериментов.
- `pdf-text/`, `pdf-render/` — извлечённый текст и изображения всех 15 страниц трёх исходных PDF.
- `proposal.md` — предлагаемая концепция, архитектура, границы разработки и roadmap.

## Повторение

Нужны Python 3.10+ и NumPy. Из корня проекта:

```powershell
python -B research/probe.py
python -B research/edge_cases.py
```

Диагностические скрипты перезаписывают только собственные JSON-отчёты в `research/`. Для их запуска PDF-библиотеки не нужны. В текущем эксперименте использован NumPy 2.4.2. Время выполнения зависит от машины; оно не является нормативом производительности приложения.

## Интерпретация

Временная сетка исходных сценариев: `range(0, 86400, 120)`, ровно 720 отсчётов. Перерывы в начале и конце периода не склеиваются. Маршрут заканчивается в первом достигнутом доступном шлюзе; наземные промежуточные узлы запрещены. BFS минимизирует число рёбер, при равенстве порядок определяется идентификаторами; длина маршрута в диагностике не оптимизируется. Основные показатели доступности от выбора допустимого кратчайшего маршрута не зависят.

Категории причин в `findings.json` имеют приоритет: connected → no_client_coverage → all_gateways_offline → no_gateway_contact → isl_disconnected. Это выбранная диагностическая классификация, поскольку документы не задают приоритет одновременных причин. Будущее приложение должно дополнительно показывать сопутствующие условия.

Все четыре штатных сценария проверены на каждом отсчёте: 2880 состояний сети и 8640 пар «клиент — время». Сверка геометрии по формулам на 60 дополнительных состояниях не является исчерпывающим доказательством совпадения на всех возможных входах.
