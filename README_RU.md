# Орбита

Орбита - инженерное веб-приложение для проектирования, моделирования и сравнения спутниковых группировок по математической модели КосмоХакатона 2026.

Приложение рассчитывает состояние сети во времени, ищет сквозные маршруты от наземных клиентов до шлюзов, объясняет перерывы, анализирует отказы и сравнивает варианты проекта. Для геометрии орбит и контактов напрямую используется предоставленный организаторами `geometry.py`.

![Рабочая область Орбиты](docs/screenshots/research.png)

## Возможности

- Загрузка четырёх контрольных или любого допустимого JSON-сценария того же формата.
- Редактирование очереди, плоскостей, аппаратов, наземных пунктов, отказов и параметров связи.
- Полный расчёт координат, контактов и маршрутов на временной сетке.
- Раздельные показатели покрытия и сквозной доступности.
- Глобус, полярная карта, топология, timeline, маршруты и таблица контактов.
- Причины отсутствия связи и подробные факты о компонентах сети.
- Синхронное сравнение двух завершённых расчётов.
- N-1, проверяемые рекомендации и контрфактическая диагностика.
- Воспроизводимый поиск сочетаний очереди, ISL и фаз с границей Парето.
- Экспорт сценариев, маршрутов, сравнений и отчётов экспериментов.

## Быстрый запуск

Рекомендуемый способ - Docker Engine с Compose:

```sh
docker compose -p orbita up -d --build
```

Открыть [http://127.0.0.1:8000](http://127.0.0.1:8000). Проверка API: [http://127.0.0.1:8000/api/health](http://127.0.0.1:8000/api/health).

Остановка с сохранением результатов:

```sh
docker compose -p orbita down
```

Не добавляйте `-v`, если Docker-том с расчётами нужно сохранить.

## Рабочий процесс

1. Выбрать встроенный сценарий или загрузить JSON.
2. Нажать «Рассчитать».
3. Выбрать клиента и отсчёт времени.
4. Исследовать маршрут, timeline, перерывы, контакты и топологию.
5. В «Проектировании» изменить параметры, сохранить ревизию и рассчитать её.
6. Сравнить базу и новый вариант в «Сравнении A/B».
7. Проверить N-1 и улучшения в «Устойчивости».
8. Запустить поиск комбинаций в «Автоподборе».
9. Выгрузить выбранный сценарий и полный результат.

## Расчётная модель

Главные источники истины - три PDF организаторов в корне и `Расчетный модуль/geometry.py`. Приложение вызывает эталонный модуль через адаптер и не повторяет геометрию в браузере.

Модель использует сферическую Землю радиусом 6371 км, круговые орбиты, параметр `398600.435507 км^3/с^2`, период вращения Земли `86164.09054 с` и земные координаты для проверки контактов.

Спутник активен при `launch_batch <= launch_stage` и отсутствии текущего времени в интервале отказа `[start_s, end_s)`. Наземный контакт существует при возвышении не ниже порога. ISL существует, если аппараты активны, расстояние строго меньше `isl_range_km`, а соединяющий отрезок не пересекает и не касается Земли.

Радиобюджет, атмосфера, трафик, ёмкость каналов, энергопотребление и пакетная задержка не добавляются, поскольку их нет в модели организаторов.

## Маршрутизация

Snapshot преобразуется в неориентированный граф. Клиент является источником, внутренними узлами могут быть только активные спутники, работающий gateway является конечной точкой. Наземный транзит запрещён.

Маршрут выбирается по порядку:

1. Минимальное число рёбер.
2. Минимальная сумма геометрических длин среди таких путей.
3. Лексикографически минимальная полная цепочка ID при полном равенстве.

BFS строит слои минимального числа переходов, затем динамический проход выбирает длину и стабильный tie-break. При отсутствии пути сохраняется причина: нет покрытия, все шлюзы отключены, у шлюзов нет контактов или спутниковые компоненты разорваны.

![Разрыв спутниковой сети](docs/screenshots/disconnected.png)

## Время и показатели

Сетка строится как `range(0, horizon_s, step_s)`. Для суток и шага 120 секунд получается 720 отсчётов от 0 до 86280 секунд.

Для каждого клиента рассчитываются покрытие, доступность, достижение цели, интервалы и длительность перерывов, статистика переходов и длины маршрутов, переключения маршрута и распределение причин. Результат относится к дискретной сетке и не доказывает непрерывность связи между отсчётами.

## Контрольные сценарии

Каждая ячейка содержит видимые отсчёты, достижимые отсчёты и максимальный перерыв.

| Сценарий | C65 | C70 | C72 |
|---|---:|---:|---:|
| Полная группировка | 704 / 696 / 480 с | 719 / 711 / 120 с | 720 / 712 / 120 с |
| Первая очередь | 275 / 196 / 34320 с | 351 / 114 / 39480 с | 421 / 91 / 47760 с |
| Отказ 10 аппаратов | 609 / 571 / 1440 с | 650 / 582 / 1440 с | 670 / 594 / 1200 с |
| ISL 2000 км | 704 / 558 / 5640 с | 719 / 448 / 10680 с | 720 / 469 / 240 с |

У C65 уменьшение ISL до 2000 км сохраняет покрытие 97,78%, но снижает доступность с 96,67% до 77,50%. Поэтому наземной видимости недостаточно для оценки сети.

## Устойчивость и поиск

N-1 добавляет полный отказ каждого развёрнутого аппарата по отдельности и повторно считает маршруты всех клиентов. Рекомендации проверяют снятие заданных отказов, включение следующей очереди и увеличение ISL на 1000 или 2000 км. Каждый кандидат полностью пересчитывается. Улучшение подтверждается только при наличии восстановленных отсчётов и отсутствии потерь у всех клиентов.

![Отчёт N-1](docs/screenshots/n-minus-one.png)

![Проверенные рекомендации](docs/screenshots/recommendations.png)

Автоподбор проверяет до 24 новых сочетаний очереди, дальности ISL и фаз плоскостей. Seed воспроизводит выбор из конечной сетки. Парето учитывает доступность худшего клиента, максимальный перерыв, число аппаратов и дальность ISL. Поиск не заявляет глобальный оптимум.

## Архитектура

```text
React и TypeScript
  -> FastAPI
  -> валидация и ресурсные ограничения
  -> SQLite и очередь заданий
  -> отдельный Python-процесс
  -> эталонная геометрия
  -> граф и маршруты
  -> метрики и перерывы
  -> сжатый JSON
  -> интерфейс и экспорт
```

| Путь | Ответственность |
|---|---|
| `orbita/scenario.py` | JSON, валидация, ссылки и SHA сценария |
| `orbita/geometry_adapter.py` | Загрузка и SHA эталонной геометрии |
| `orbita/topology.py` | Контактный граф и компоненты спутников |
| `orbita/routing.py` | Маршруты и причины отсутствия связи |
| `orbita/analysis.py` | Покрытие, доступность, перерывы и статистика |
| `orbita/engine.py` | Полный расчёт и обязательный экспорт |
| `orbita/comparison.py` | Совместимость и дельты A/B |
| `orbita/resilience.py` | Диагностика, N-1 и рекомендации |
| `orbita/optimization.py` | Сетка поиска и Парето |
| `orbita/storage.py` | SQLite и атомарные артефакты |
| `orbita/jobs.py` | Процессы, прогресс, отмена и восстановление |
| `orbita/api.py` | HTTP API, сеансы и лимиты |
| `web/src` | Интерфейс, редактор и визуализации |

## Данные и экспорт

Версия сценария - `cosmo-A-1.0`. Структурная схема находится в [docs/scenario.schema.json](docs/scenario.schema.json). Межполевые ссылки проверяются приложением и эталонным модулем. Дополнительные поля сохраняются.

Обязательный экспорт `cosmo-A-result-1.0` содержит полный сценарий, одну запись маршрута на каждого клиента и отсчёт, сводные показатели и provenance версий и контрольных сумм.

## Локальная разработка

Нужны Python 3.12 и Node.js 22.12 или новее.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
cd web
npm ci
npm run build
cd ..
.\.venv\Scripts\python.exe -m uvicorn orbita.api:app --host 127.0.0.1 --port 8000 --workers 1
```

На Linux и macOS использовать `.venv/bin/python`. CLI запускается без веб-сервера:

```sh
python -m orbita.cli "Данные/01_full_constellation.json" --output var/full-result.json
```

## Публичное развёртывание

`compose.public.yaml` добавляет Caddy и HTTPS для сервера с доменом. Скопировать `.env.example` в `.env`, задать `ORBITA_DOMAIN` и выполнить:

```sh
docker compose -p orbita -f compose.yaml -f compose.public.yaml up -d --build
```

API запускается с одним Uvicorn worker, вычисления выполняются отдельным пулом процессов. Для резервной копии нужно остановить контейнер приложения и сохранить весь том `/data`.

## Ограничения

- Результаты относятся к дискретной временной сетке.
- Модель описывает геометрические контакты, но не пропускную способность и надёжность оборудования.
- Ограниченный поиск не доказывает глобальную оптимальность.
- Резервный путь может использовать часть аппаратов основного.
- Сеансы анонимные и привязаны к cookie браузера.
- Хранение рассчитано на один сервер, SQLite и один API worker.
- Автоматическая очистка старых результатов не реализована.
- PDF-отчёты и экономическая оптимизация не реализованы.

В репозитории сохранены постановка, описание данных, критерии оценки, четыре исходных сценария и неизменённый эталонный модуль организаторов.
