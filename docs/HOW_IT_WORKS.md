# Как работает «Орбита» — объяснение с нуля

Этот документ можно читать без знаний космонавтики и программирования. Сначала разберём, какую задачу решает приложение, затем пройдём весь расчёт на понятных примерах. В конце — устройство кода и способ самостоятельно проверить результат.

## 1. На какой вопрос отвечает приложение

Представьте удалённый населённый пункт, которому нужен доступ к наземной сети. Рядом нет кабеля, поэтому связь должна пройти через спутники:

**Клиент на Земле → спутник → возможно, другие спутники → наземный шлюз.**

Клиент — место, которому нужна связь. Шлюз, или gateway, — наземная станция, через которую спутниковая сеть соединяется с остальной наземной инфраструктурой. Спутники постоянно движутся, поэтому этот путь может появляться, меняться и исчезать.

Приложение отвечает на три связанных вопроса:

1. Какие соединения возможны в каждый момент расчёта?
2. Есть ли по ним полный путь от каждого клиента до хотя бы одного работающего шлюза?
3. Насколько часто связь доступна, как долго длятся перерывы и какие изменения улучшают результат?

Показать спутник над городом недостаточно. Он может видеть клиента, но не иметь ни прямого контакта со шлюзом, ни цепочки других спутников, ведущей к нему.

## 2. Короткий словарь

| Слово | Что оно означает здесь |
|---|---|
| Группировка | Все спутники, описанные в сценарии |
| Орбита | Круг, по которому движется спутник в принятой модели |
| Орбитальная плоскость | Плоскость, в которой лежит этот круг; представьте наклонённый обруч вокруг Земли |
| Сценарий | Полное описание условий: спутники, наземные пункты, параметры связи, время и отказы |
| Контакт | Возможность соединить два узла при текущем положении и состоянии |
| ISL | Межспутниковый контакт; сокращение от inter-satellite link |
| Граф | Список узлов и соединений между ними |
| Маршрут | Упорядоченная цепочка соединённых узлов от клиента до шлюза |
| Переход | Одно ребро маршрута, то есть один переход между соседними узлами |
| Отсчёт | Один момент на временной сетке, в который выполняется расчёт |
| Покрытие | Доля отсчётов, когда клиент видит хотя бы один активный спутник |
| Доступность | Доля отсчётов, когда у клиента есть полный путь до шлюза |
| Ревизия | Сохранённая неизменяемая версия сценария |
| Расчёт, или run | Результат обработки конкретной ревизии |

## 3. Из чего состоит входной сценарий

Сценарий хранится в JSON — текстовом файле с именованными полями и списками. Для работы не обязательно редактировать его вручную: интерфейс предоставляет формы.

**Окружение** задаёт высоту и наклонение орбит, начальный поворот Земли, горизонт расчёта, шаг времени, минимальное возвышение спутника, дальность межспутниковой связи и целевую доступность.

**Плоскости** задают ориентацию орбит и общую фазу спутников в каждой из них:

- `raan_deg` поворачивает плоскость вокруг полярной оси. При одинаковом наклонении можно расположить несколько орбитальных «обручей» в разных направлениях.
- `phase_deg` сдвигает начальные положения всех спутников данной плоскости вдоль орбиты.

**Спутник** имеет свой ID, ссылку на плоскость, начальное положение `slot_deg` и номер очереди запуска. Его начальный угол вдоль орбиты равен сумме `slot_deg + phase_deg`.

**Наземные пункты** имеют широту, долготу и роль: клиент или шлюз. Имена вроде C65 или G_MUR не обладают специальным значением для алгоритма: роли берутся из данных.

**Отказы** задают аппарат или шлюз и интервал недоступности. В сценарии может быть несколько шлюзов, произвольные ID и другой состав спутников. Программа не выбирает алгоритм по имени одного из четырёх контрольных файлов.

Перед расчётом вход проверяется. Например, неизвестная плоскость, повторяющийся ID, отрицательный шаг или ссылка на отсутствующий спутник дают ошибку с указанием поля. Дополнительные неизвестные поля сохраняются, но сами по себе не меняют математическую модель.

## 4. Как узнаём, где находится спутник

Используется исходный `Расчетный модуль/geometry.py`. Это важное архитектурное решение: приложение вызывает предоставленную геометрию, а не создаёт похожую версию с другими допущениями.

В этой модели Земля — сфера радиусом **6371 км**, а орбиты — круговые. Для высоты 550 км расстояние от центра Земли до спутника равно:

```text
r = радиус Земли + высота = 6371 + 550 = 6921 км
```

Угловая скорость движения по кругу:

```text
n = √(μ / r³)
μ = 398600.435507 км³/с²
```

Здесь `n` показывает, на какой угол спутник сдвигается за секунду. На высоте 550 км один оборот занимает примерно 95,5 минуты. За время `t` положение вдоль орбиты изменяется на `n × t`. К нему прибавляется начальное положение спутника с учётом фазы плоскости.

Далее круг поворачивается в пространстве на заданные наклонение и RAAN. Получаются три координаты: x, y, z. Они описывают положение в километрах, а не пиксели экрана.

Земля тоже вращается. Поэтому геометрический модуль переводит положение в систему, связанную с Землёй. В ней наземные станции неподвижны, а спутники движутся относительно поверхности. Угловая скорость Земли равна `2π / 86164.09054` в секунду, с учётом заданного начального угла.

Для проверки формул: если угол вдоль орбиты — `u`, RAAN — `Ω`, наклонение — `i`, то сначала рассчитывается:

```text
x = r × (cos Ω × cos u − sin Ω × sin u × cos i)
y = r × (sin Ω × cos u + cos Ω × sin u × cos i)
z = r × sin u × sin i
```

Все углы при вычислении синусов и косинусов переведены в радианы. Если текущий угол Земли — `θ`, переход к земным координатам имеет вид:

```text
x_зем = cos θ × x + sin θ × y
y_зем = −sin θ × x + cos θ × y
z_зем = z
```

Положение наземной точки получается из её широты и долготы на той же сфере. Благодаря единой системе координат можно сравнивать положения спутников и станций напрямую.

## 5. Какие аппараты вообще участвуют

Координаты вычисляются и для неработающих аппаратов — поэтому их можно показывать на сцене. Но контакты создаются только для активных.

Спутник активен, когда одновременно выполняются два условия:

1. Его очередь запуска не больше выбранной очереди развёртывания.
2. Текущее время не попадает ни в один его интервал отказа.

Если выбрана первая очередь, спутники второй и третьей не участвуют весь период. Очередь не означает, что они запустятся в середине этих суток.

Интервал `[21600, 86400)` означает: в секунду 21600 отказ уже действует, в секунду 86400 он уже закончился. Начало включается, конец не включается. Перекрывающиеся интервалы действуют совместно: аппарат остаётся недоступным, пока действует хотя бы один из них.

## 6. Когда станция видит спутник

Представьте, что вы стоите на земле и смотрите на горизонт. Спутник может быть прямо над головой, низко над горизонтом или вообще за Землёй.

**Угол возвышения** — угол между направлением к спутнику и местным горизонтом. Контакт разрешён, если возвышение **не меньше** заданного порога. При пороге 10° угол 10° проходит, а 9,9° — нет.

В вычислениях берётся вектор от станции к спутнику. Его проекция на направление «вверх» определяет синус угла возвышения:

```text
sin(возвышение) = (вектор к спутнику · единичный вектор вверх) / расстояние
```

Точка означает скалярное произведение — операцию, измеряющую, насколько два направления совпадают. Затем применяется обратный синус.

Для отключённого шлюза контактов нет даже при подходящем положении спутника. При этом вспомогательная таблица углов может содержать его возвышения: наличие числа в этой таблице ещё не означает существование ребра связи. Алгоритм маршрутов использует именно список контактов.

## 7. Когда могут соединиться два спутника

Проверяются все пары активных аппаратов. Нужны сразу два условия:

1. Расстояние между ними **строго меньше** допустимой дальности ISL.
2. Земля не перекрывает прямой отрезок между аппаратами.

Для второго условия находится ближайшая к центру Земли точка на отрезке. Её расстояние до центра должно быть **строго больше** 6371 км. Касание сферы не считается допустимым контактом.

Разница между «меньше» и «не больше» здесь намеренная: ровно 2000 км при дальности 2000 км не проходит. Границы не расширяются ради удобного результата.

Это геометрическая модель потенциальной связи. Она не рассчитывает мощность передатчика, помехи, погоду, скорость передачи, загрузку каналов или реальную задержку пакетов.

## 8. Как из контактов получается маршрут

Каждый спутник и наземный пункт становится узлом графа. Каждый разрешённый контакт — двусторонним ребром с длиной в километрах.

Например:

```text
Клиент → S1 → S7 → Шлюз
```

В этой цепочке три перехода, включая два наземных. Промежуточными узлами могут быть только спутники. Другой клиент и даже другой шлюз не используются как ретрансляторы: шлюз является конечной точкой.

Если допустимых маршрутов несколько, порядок выбора такой:

1. Наименьшее число переходов.
2. Среди них — наименьшая суммарная длина рёбер.
3. При полном равенстве — порядок ID всей цепочки.

Поэтому путь из трёх переходов будет выбран раньше пути из четырёх, даже если второй короче в километрах. Это явный критерий приложения, а не скрытая оценка качества радиооборудования.

Технически используется поиск в ширину: сначала рассматриваются узлы на расстоянии одного ребра, потом двух и так далее. Среди путей с минимальным числом шагов отдельный проход выбирает минимальную длину. Последнее правило по ID делает одинаковые запуски воспроизводимыми.

Если путь не найден, результат — пустая цепочка `[]`. Это не маршрут с нулём переходов.

## 9. Зачем нужна временная сетка

Непрерывное движение заменяется расчётом в заданные моменты. Для суток с шагом 120 секунд это:

```text
0, 120, 240, …, 86280 секунд
```

Всего **720 отсчётов**. Точка 86400 не входит: это правая граница периода. Для каждого отсчёта заново вычисляются положения, активность, контакты и маршруты.

Если отказ действует от 61 до 181 секунды, он затронет отсчёт 120, но не 0 и не 240. Событие не округляется заранее — проверяется его принадлежность каждому моменту.

Результат характеризует именно эту сетку. Наличие пути в 0 и 120 секунд само по себе не доказывает, что связь непрерывно существовала между ними. Уменьшение шага даёт больше точек наблюдения и увеличивает объём работы.

## 10. Как считаются проценты и перерывы

Для каждого клиента отдельно:

```text
Покрытие = число отсчётов с видимым спутником / все отсчёты
Доступность = число отсчётов с полным маршрутом / все отсчёты
```

В полном контрольном сценарии у C65 спутник виден в 704 из 720 отсчётов, а полный путь есть в 696:

```text
Покрытие:   704 / 720 × 100% = 97,78%
Доступность: 696 / 720 × 100% = 96,67%
```

Восемь отсчётов из этих 704 дают покрытие без сквозной связи. Это и показывает, почему два показателя нельзя смешивать.

Рассмотрим учебную последовательность из шести отсчётов с шагом 120 с:

| Время, с | 0 | 120 | 240 | 360 | 480 | 600 |
|---|---|---|---|---|---|---|
| Есть путь | да | да | нет | нет | да | нет |

Доступность — 3 из 6, то есть 50%. Первый перерыв занимает `[240,480)` и длится 240 с. Второй — `[600,720)` и длится 120 с. Всего два перерыва; максимальный — 240 с; суммарный — 360 с.

Смена причины внутри непрерывного отсутствия пути не разбивает перерыв на два. Перерывы в начале и конце суток не склеиваются через границу горизонта.

Среднее число переходов и средняя длина считаются только по существующим маршрутам. Если маршрутов не было вообще, среднего значения нет. Цель 90% проверяется отдельно для каждого клиента; высокий показатель одного пункта не компенсирует плохой показатель другого.

## 11. Как объясняется отсутствие связи

Проверка идёт в определённом порядке:

1. Путь найден — связь доступна.
2. У клиента нет видимого активного спутника — нет покрытия.
3. Все шлюзы отключены — нет работающего выхода.
4. Работающие шлюзы не имеют спутниковых контактов — нет контакта со шлюзом.
5. Контакты на обоих концах есть, но цепочка не соединяется — разрыв спутниковой сети.

Несколько причин могут действовать одновременно. Основная подпись выбирается по этому порядку, а подробная диагностика сохраняет дополнительные факты: видимые аппараты, шлюзы и группы связанных спутников.

Группа спутников, между которыми можно добраться по рёбрам, называется компонентой связности. Если клиент видит только одну компоненту, а шлюз — другую, сквозного пути нет.

## 12. Что делают A/B, резервный путь и N−1

**A/B** сравнивает два готовых расчёта. Сначала проверяется, совпадают ли временная сетка, клиентские пункты с их координатами, версия геометрии и политика маршрутизации. При разных условиях приложение не строит некорректную дельту. При различии шага или горизонта B можно подготовить на сетке A и пересчитать.

Для каждого общего отсчёта сравниваются два ответа: был ли путь в A и есть ли он в B. Так получаются число восстановленных и потерянных отсчётов. Изменение 80% → 85% — это **+5 процентных пунктов**, а не обязательно пять восстановленных отсчётов. Возможны одновременно новые потери и новые выигрыши, поэтому они показаны отдельно.

**Резервный маршрут** — другой допустимый путь в текущем отсчёте. Программа исключает по одному ребру основного маршрута, ищет путь снова и выбирает лучший отличающийся вариант. У него могут остаться общие спутники с основным. Дополнительно проверяется удаление каждого спутника выбранной цепочки: останется ли обход?

**N−1** означает «что произойдёт, если потерять ещё один аппарат». По очереди для каждого развёрнутого спутника добавляется отказ на весь горизонт. Все уже заданные отказы сохраняются. Для каждого случая пересчитываются доступность и перерывы каждого клиента.

Геометрия остальных пар не зависит от наличия третьего спутника. Поэтому в N−1 можно один раз получить исходные контакты отсчёта и затем удалять аппарат с его рёбрами. Это ускорение не подменяет модель; его результат сверяется с обычным полным пересчётом сценария с добавленным отказом.

Например, в полном сценарии дополнительный отказ S44 уменьшает число достижимых отсчётов на 17 у C65 и на 14 у C70 и C72. Это измеренный ущерб на сетке, а не вероятность поломки S44.

## 13. Откуда берутся рекомендации

Рекомендации не являются автоматически придуманными советами. Код формирует ограниченный набор проверяемых кандидатов:

- убрать объявленные отказы аппаратов и шлюзов;
- включить следующую очередь, если она ещё не развёрнута;
- увеличить допустимую дальность ISL на 1000 или 2000 км, не выходя за пределы формата.

Каждый кандидат полностью рассчитывается и сравнивается с базой. Пометка «Улучшение подтверждено» появляется, если восстановлен хотя бы один отсчёт и при этом ни один клиент не потерял ни одного ранее доступного отсчёта. Достижение цели проверяется отдельно: улучшение может оказаться недостаточным для 90%.

Рекомендация увеличить дальность — требование внутри геометрической модели. Она не доказывает, что подходящее оборудование существует, дёшево стоит или обеспечит нужную мощность. Устранение всех отказов — контрфактическая проверка, а не обещание технической возможности ремонта.

Программа не заявляет, что нашла лучший вариант среди всех возможных орбит и составов. Она показывает результаты конкретных воспроизводимых экспериментов.

## 14. Что происходит после нажатия «Рассчитать»

```text
Сценарий → проверка → сохранённая ревизия → задание
        → геометрия каждого отсчёта → граф → маршруты
        → временные ряды → метрики и перерывы → сохранённый результат
```

Браузер отправляет JSON серверу. Сервер проверяет данные и допустимый объём работы. Затем отдельный процесс выполняет расчёт, чтобы интерфейс мог продолжать отвечать. Прогресс и отмена контролируются сервером.

Готовый результат записывается в файл, а сведения о нём — в SQLite, небольшую файловую базу данных. Незавершённый файл не объявляется готовым результатом. После перезапуска сервера завершённые расчёты остаются доступны, незавершённые помечаются прерванными.

Интерфейс получает итоговые ряды и метрики. При выборе времени отдельно запрашивает подробный snapshot — состояние сети в этом отсчёте. Он строится по сохранённому сценарию расчёта, а не по новым несохранённым правкам.

## 15. Где находится логика в проекте

| Файл или каталог | За что отвечает |
|---|---|
| `Расчетный модуль/geometry.py` | Исходные координаты, активность и контакты |
| `orbita/scenario.py` | Чтение JSON, проверка полей и ссылок |
| `orbita/geometry_adapter.py` | Подключение исходной геометрии и её контрольной суммы |
| `orbita/topology.py` | Граф, работающие шлюзы и компоненты |
| `orbita/routing.py` | Выбор маршрута и основная причина отсутствия связи |
| `orbita/analysis.py` | Доступность, покрытие, перерывы и другие агрегаты |
| `orbita/engine.py` | Полный расчёт по времени и экспорт |
| `orbita/comparison.py` | Сопоставимость A/B, отличия и дельты |
| `orbita/resilience.py` | N−1, резервные пути, контрфактическая проверка и кандидаты |
| `orbita/jobs.py`, `storage.py`, `api.py` | Процессы, хранение и HTTP-запросы |
| `web/src` | Экраны, формы, карта, глобус, граф и timeline |
| `tests`, `web/tests` | Проверки расчётов, API и пользовательских действий |

Python выполняет расчёты. React и TypeScript отвечают за интерфейс. Браузер не создаёт свои физические контакты. Поворот глобуса меняет только камеру, не время и не доступность.

## 16. Как убедиться, что цифры не выдуманы

Четыре контрольных сценария проверяются на всём горизонте. Всего это 2880 состояний сети и 8640 пар клиент/время. Для путей используется независимая проверка другим алгоритмом: сравниваются достижимость, минимальное число переходов и допустимость каждого ребра.

Отдельные тесты проверяют границы отказов, несколько шлюзов, несвязный граф, неверный JSON, равные маршруты, временные перерывы и сохранность данных. N−1 сравнивается с добавлением реального отказа в сценарий и полным пересчётом. Браузерные тесты проходят путь от загрузки и редактирования до сравнения и экспорта.

В экспорт входит полный фактический сценарий, одна цепочка на клиента и отсчёт, показатели и сведения для воспроизведения. Контрольная сумма, или hash, — «отпечаток» содержимого. Она помогает установить, по какому входу и какой версии геометрии получен результат; сама по себе она не доказывает правильность математики.

Практический первый опыт: рассчитайте полный сценарий, запомните доступность C65, уменьшите дальность ISL до 2000 км и рассчитайте отдельную ревизию. В A/B покрытие C65 останется тем же, а доступность упадёт с 96,67% до 77,50%. Откройте потерянный отсчёт: станет видно, как клиент продолжает видеть спутник, но часть сквозных маршрутов исчезает. Это наглядно связывает геометрию, граф и итоговый процент.
